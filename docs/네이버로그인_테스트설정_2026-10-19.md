# 네이버 간편 로그인 — 테스트 준비 및 사용자 직접 설정

## 1. 현재 상태와 경계

- 요청: 네이버로 로그인 버튼을 테스트 환경부터 추가. 운영 앱·운영 회원 데이터는 변경하지 않는다.
- 최신 저장소: C:/Users/eodls/Desktop/코덱스 저장소/dadamom-test / staging.
- 테스트 Supabase: srxdtddrtnhtlbbviyvs. 운영 Supabase는 이번 작업에서 열지 않았다.
- 버튼과 OAuth 시작 코드를 작성했다. **NAVER_LOGIN: 'preview'**이므로 버튼에 연결 준비 안내를 표시하고 외부 인증 요청을 차단한다. 아직 네이버 로그인 완성이 아니다.
- 네이버 Client ID·Client Secret은 미등록/미입력 상태다. 테스트 Supabase 제공자 목록에 custom provider가 없음을 읽기 전용 확인했다. 새 제공자 빈 양식에서 Callback URL을 확인한 후 취소했다. 제공자 생성·Auth 설정 저장·회원 조회/가입/로그인·SQL은 하지 않았다.
- 저장소 규칙대로 이번 세션은 코드만 수정한다. Supabase Auth 설정 적용은 사용자 직접 단계 또는 별도 설정 세션에서 처리한다. 코드와 DB/Auth 설정을 한 세션에서 함께 변경하지 않는다.
- 다른 세션 변경을 보존했다. git pull --rebase는 기존 미커밋 변경 때문에 중단됐으며, 자동 stash하지 않았다. fetch 결과 원격 누락 커밋은 0개였고 로컬에는 앞선 문서 커밋 7개가 있었다.

## 2. 구현

- 로그인/회원가입/로그인 모달에 동일한 네이버 버튼 사용. 색상 #03A94D, N 로고 20px, 간격 8px. 흰색 글자 대비를 위해 굵은 19px 레이블 사용.
- 기존 카카오·구글 스위치 SOCIAL_LOGIN과 네이버 스위치 NAVER_LOGIN은 독립적이다.
- NAVER_LOGIN이 true인 경우에만 Supabase signInWithOAuth의 provider custom:naver를 호출한다. 'preview'는 비활성 버튼 표시, false/누락/그 밖의 값은 숨김이다.
- scopes는 네이버 공개 discovery의 openid profile을 사용한다. 공개 목록에 없는 email scope를 임의로 추가하지 않는다. 이메일 제공 동의는 네이버 앱 설정과 실제 ID token claim 반환을 별도로 확인해야 한다.
- 기존 authCallbackUrl()을 사용해 같은 테스트 환경의 index.html로 돌아간다. 허용된 원글/챌린지/혜택 복귀와 유입 경로만 보존하고 임의 외부 복귀·인증 코드 전달을 막는다.
- 중복 클릭 방지, SDK 오류/예외 시 안전한 안내·버튼/로고 복원, 인증 페이지에서 뒤로 돌아온 bfcache 화면의 버튼 복원을 추가했다. SDK 원문 오류는 출력하지 않는다.
- Client Secret/토큰 교환은 Supabase 서버가 담당한다. 브라우저에 비밀키, service_role, 직접 토큰 교환 코드, 임의 회원 생성/계정 연결 코드를 넣지 않았다.
- 운영 예시 설정에는 NAVER_LOGIN: false만 추가했다. 운영 저장소·배포·DB는 변경하지 않았다.

## 3. 사용자가 먼저 할 일 — 네이버 앱 등록

1. https://developers.naver.com/apps/#/register?api=nvlogin 에 본인 네이버 계정으로 로그인한다.
2. 최초 이용약관 동의·휴대폰 인증·개발자 계정 정보 등록이 나오면 직접 완료한다.
3. 테스트 전용 애플리케이션을 등록한다. 이미 운영용 네이버 앱이 있다면 수정하지 말고 테스트용을 별도로 만든다.

| 항목 | 넣을 값 |
|---|---|
| 애플리케이션 이름 | 다다맘 TEST |
| 사용 API | 네이버 로그인 |
| 환경 | PC 웹 및 Mobile 웹 (Safari/PWA도 우선 웹 방식으로 검증) |
| 서비스 URL | https://adultryun188-lang.github.io/dadamom-test/ |
| Callback URL | https://srxdtddrtnhtlbbviyvs.supabase.co/auth/v1/callback |
| 제공 정보 | 이용자 식별자 기본 제공 + 이메일 주소만 우선 사용. 생일·성별·휴대폰·실명·프로필 사진 등 불필요한 권한은 선택하지 않는다. 앱에서 별명을 직접 입력하므로 네이버 별명도 우선 불필요하다. |

- Callback URL은 테스트 앱 주소나 dadamom.co.kr이 아니다. 위 Supabase callback을 그대로 입력한다. 실제 테스트 Supabase Create Custom Auth Provider 화면의 값과 일치 확인했다.
- 네이버 개발 모드에서 허용된 개발자/테스트 계정으로만 테스트한다. 테스트 멤버 추가가 필요하면 개발자센터에서 사용자 직접 추가한다.
- 등록 후 Client ID와 Client Secret은 안전하게 보관하고 아래 테스트 Supabase 양식에 **직접 입력·저장**한다. 채팅/스크린샷/MD/env.js/GitHub에 보내지 않는다. 실제 키가 표시된 화면은 에이전트에게 확인을 요청하기 전에 벗어난다.

## 4. 사용자 직접 설정 — 테스트 Supabase만

### 4-1. 복귀 주소 (현재 비어 있음)

https://supabase.com/dashboard/project/srxdtddrtnhtlbbviyvs/auth/url-configuration

- Site URL은 현재 https://adultryun188-lang.github.io/dadamom-test/ 로 정상이다. 유지한다.
- **현재 Redirect URLs가 0개**다. Add URL로 아래 두 주소를 추가한다. 운영 도메인은 넣지 않는다.

```text
https://adultryun188-lang.github.io/dadamom-test/index.html
https://adultryun188-lang.github.io/dadamom-test/index.html?**
```

- 두 번째 주소는 기존 안전한 returnTo/from 쿼리 복귀를 위한 허용 패턴이다. 앱의 외부 복귀 차단을 해제하는 의미가 아니다.
- 이 목록이 비어 있으면 Supabase가 Site URL로 대체해 원글 복귀 정보가 사라질 수 있다. 먼저 등록한 후 테스트한다.

### 4-2. Custom Provider (네이버 키 입력은 사용자 직접)

https://supabase.com/dashboard/project/srxdtddrtnhtlbbviyvs/auth/providers

- 상단 프로젝트 이름 dadamom-test 및 URL의 srxdtddrtnhtlbbviyvs를 확인한다. main / PRODUCTION 표시는 Supabase 프로젝트 내부 브랜치 표시이므로 이것만으로 운영·테스트를 구분하지 않는다.
- Custom Providers 아래 New Provider.

| 항목 | 값 |
|---|---|
| Provider Identifier | naver (화면에 custom: 접두사가 이미 표시된다. 최종 식별자는 custom:naver) |
| Display Name | Naver |
| Configuration Method | Auto-discovery (OIDC) |
| Issuer URL | https://nid.naver.com |
| Discovery URL | 비움 (표준 주소를 자동으로 사용) |
| Client ID / Client Secret | 방금 만든 테스트용 네이버 앱의 값, 사용자 직접 입력 |
| Scopes | openid, profile |
| Allow users without email | 우선 OFF 유지. 동작시키려고 임의로 완화하지 않는다. |
| Callback URL | https://srxdtddrtnhtlbbviyvs.supabase.co/auth/v1/callback 확인 |

- 사용자가 Create and enable provider까지 직접 실행한다. 발급/등록 단계의 약관이나 권한 승인도 사용자가 직접 판단한다.
- 저장 오류가 나면 비밀키를 가린 오류 문구만 전달한다. PKCE/서명/issuer/audience/nonce 검증을 끄거나 email_verified를 강제로 true로 만들어 우회하지 않는다.
- 이 코드 세션에서는 Supabase 제공자를 저장하지 않았다. 자격증명 등록과 권한 생성은 별도 사용자 직접 단계다.

## 5. 설정 후 실제 검증 순서

1. 사용자 설정 완료 보고 후, 별도 설정 세션/사용자가 provider 활성화와 테스트 URL 목록을 읽기 전용 확인한다. 키 원문은 읽지 않는다.
2. staging의 NAVER_LOGIN을 'preview'에서 true로 변경·테스트 배포한다. 설정 전에 true로 켜지 않는다.
3. 공개 테스트 앱 버튼을 실제 클릭해 테스트 Supabase authorize → 네이버 인증 페이지로 진입하는지 확인한다.
4. 사용자가 승인된 네이버 테스트 계정으로 로그인·정보 제공 동의를 직접 한다. 계정 비밀번호/인증 코드를 채팅으로 전달하지 않는다. 이때 테스트 DB에는 신규 회원/로그인 기록이 생길 수 있지만 운영 DB는 사용하지 않는다.
5. 테스트 앱 복귀, 신규 사용자 약관 동의·프로필 작성, 기존 테스트 회원 재로그인, 같은 브라우저/새 브라우저 재방문을 확인한다. 기존 온보딩을 생략하거나 이미 동의한 것으로 처리하지 않는다.
6. 원글 공유 진입·챌린지/혜택 진입에서 로그인 후 원위치 복귀, 잘못된 외부 복귀 차단, 동의 취소/뒤로가기/네트워크 오류를 실제 확인한다. 현재 스텁 검증은 실제 동의 취소 콜백을 대체하지 않는다.
7. ID token이 안정적인 sub 및 필요한 email을 반환하고, email_verified가 적절하게 처리되는지 확인한다. 토큰 원문을 로그/문서에 남기지 않는다. 네이버 일반 profile API의 response.id/response.email 중첩 응답과 표준 OIDC ID token은 다르므로 단순 OAuth2 수동 설정으로 교체하지 않는다.
8. 이메일이 반환되지 않으면 출시 보류한다. 이메일 필수 조건을 임의로 해제하거나 테스트 성공으로 처리하지 말고, 실제 네이버 제공 항목/ID token과 Supabase OIDC 호환을 진단한다. 다른 서버나 중계 서비스 신설은 별도 설계·승인 범위다.
9. 동일 이메일의 기존 소셜 계정과 어떤 식으로 연결되는지 테스트 전용 계정으로 확인한다. 앱이 이메일 문자열만 보고 회원을 직접 합치지 않는다.
10. 아이폰 Safari·홈 화면 PWA 실제 로그인 왕복은 사용자가 직접 확인한다. 현재 PC Chromium 스텁은 실기기 검증이 아니다.

## 7. 일반 고객 출시 전에 별도로 남는 일

- 네이버 개발 모드는 일반 고객 전체에게 개방된 상태가 아니다. 실제 서비스 적용에는 네이버 사전 검수·승인이 필요하다. 검수 신청/자료 제출/정보 제공 동의 화면/개인정보처리방침·연결 해제 안내는 테스트 왕복 검증 후 준비한다.
- 테스트 앱과 운영 앱을 분리해 유지한다. 실제 출시용 네이버 앱/운영 Supabase 등록, 운영 callback, 비밀키 입력, 운영 버튼 활성화는 모두 별도 운영 승인 대상이다.
- 되돌리기: 테스트 환경 NAVER_LOGIN false면 숨김, 'preview'면 외부 요청 차단. 운영은 수정하지 않았으므로 롤백 불필요. 회원 삭제로 롤백하지 않는다.

## 0. 다음 AI가 먼저 알아야 할 제품 맥락

사용자는 다다맘 앱·웹에 많은 시간과 비용을 투입했다. 베이비빌리·마미톡·맘가이드·맘맘·베이비타임·패밀리앨범과 비교한 뒤, 무작정 새 기능을 늘리기보다 기존 자산을 살리는 방향을 원한다.

사용자의 중요한 우려는 ‘남편은 설치와 기록을 번거로워하고 배우자가 보여줄 때만 볼 수 있다’는 경험이다. 이를 전체 남편의 통계적 특성으로 단정하지 않는다. 두 사람이 모두 매일 기록하는 것을 서비스 성립 조건으로 삼지 않는다.

추천 중심 문장:

> 우리 아이의 작은 성장을 남기고, 비슷한 시기를 지나는 부모들과 경험을 나누는 커뮤니티.

목표 흐름:

`질문 → 비슷한 경험의 답변 → 이후 후기 → 선택적으로 성장 기록 → 선택적으로 챌린지·가족 공유`

이 흐름의 연결은 제안이다. 기존에 구현된 부분을 먼저 찾아 재사용한다. 다른 앱에 없는 독점 기능이라고 주장하지 않는다.

## 3. P0 — 실제 이용을 막는 부분부터

### P0-1. 첫 이용과 핵심 커뮤니티 흐름 검증

**확인할 것**

- 비로그인 글 발견 → 로그인·가입 → 원래 보던 화면 복귀
- 가입·로그인의 로딩·실패·재시도·중복 제출 처리
- 글 작성 → 저장 → 검수 상태 안내 → 정책에 맞는 공개
- 댓글 작성 → 화면 반영 → 새로고침 후 유지
- 홈·피드·상세 등 같은 기능이 있는 여러 화면의 상태 일치
- 기존 기록·찜·프로필·신고·차단 등 영향을 받는 기능의 회귀

**완료 기준**

- 테스트 계정으로 첫 글·댓글을 실제 완료할 수 있다.
- 성공하지 않았는데 성공으로 안내하거나, 실패가 조용히 묻히지 않는다.
- 비로그인·권한 없는 계정의 작성·조회 시도는 정책대로 처리된다.
- 검수 대기를 공개 완료처럼 표시하지 않는다.
- 기존 저장·동기화 방식은 유지하고, 관련 변경 시 다른 기기·웹/앱 간 데이터 보존을 확인한다.

현재 인증 방식을 추측해 재작성하지 않는다. 실제 소셜 계정 로그인이 필요하면 사용자가 직접 인증하는 단계를 구분한다. 운영 계정으로 검증하지 않는다.

### P0-2. 공개 범위·가족 권한·반응의 경계 보존

**확인할 것**

- 참가작의 기존 회원 전용 정책
- 가족 초대·가입·철회·만료·접근 권한
- 사진·영상의 저장 경로와 서명 URL 취급
- 가족 메시지, 커뮤니티 댓글, 챌린지 응원·투표의 저장 및 권한 경계
- 커뮤니티 게시, 가족 공유, 외부 홍보 활용의 동의·공개 범위

**완료 기준**

- 설치를 줄이기 위해 비공개 자료를 공개 URL로 바꾸지 않는다.
- 링크를 가진 타인과 철회·만료된 초대가 정책상 허용되지 않은 자료를 볼 수 없다.
- 가족 메시지가 챌린지 점수·순위·투표권에 영향을 주지 않는다.
- 동의 철회 시 기존 URL·캐시·이미 발급된 서명 URL의 한계를 확인하고 검증 결과를 남긴다. 화면에서만 숨기고 서버 접근도 막혔다고 주장하지 않는다.
- 확인되지 않은 문제를 이미 발생한 보안 결함으로 보고하지 않는다.

### P0-3. 최소 측정 체계

기존 가입 경로·활동 정보가 있는지 먼저 확인한다. 별도 분석 SDK나 대시보드를 무조건 새로 도입하지 않는다.

| 측정 항목 | 최소 해석 기준 |
|---|---|
| 첫 행동 완료 | 신규 가입 후 첫 글 또는 댓글 완료. 시작·실패·완료를 구분 |
| 다른 이용자 답변 | 운영자·시스템·시드·본인 댓글을 제외한 답변 여부 |
| 일주일 내 재행동 | 가입일 이후 7일 내 다른 날짜에 글·댓글·기록 등 사전에 정한 의미 있는 행동 |
| 비경품 행동 | 경품 참여·투표와 일반 기록·대화를 분리 |
| 가족 초대 후 행동 | 초대 생성·열람·권한 확인·반응 완료·이후 재이용을 구분 |
| 유입 출처 | 협의 QR·콘텐츠 운영자·소액 광고 등 모집 경로를 구분 |

**완료 기준**

- 이벤트명과 집계 정의, 분모·분자, 관찰 기간, 테스트/시드 제외 기준을 문서화한다.
- 한 달 말 가입자처럼 7일 관찰이 끝나지 않은 사람을 미재방문으로 단정하지 않는다.
- 반복 클릭·새로고침·재시도로 완료 수가 부풀지 않는다.
- 이벤트에는 글·댓글 본문, 사진 URL, 이메일, 아이 이름·생년월일, 초대 토큰을 담지 않는다.
- 동의·수집 범위는 현재 정책과 대조하고, 신규 외부 분석 서비스 연동은 별도 범위로 남긴다.
- 운영 데이터를 보지 않고 테스트 이벤트로 집계 검증이 가능하다.

일주일 재행동은 이 전달서의 운영 정의 제안이다. 기존 지표와 다르면 정의를 맞추고 결과에 기록한다. 목표 수치나 예상 전환율은 근거 없이 만들지 않는다.

## 4. P1 — 커뮤니티 중심 첫 경험

### P1-1. 홈의 우선순위 조정

**수정 제안**

- 중심 메시지: ‘작은 성장도, 함께 기뻐해요.’
- 설명: ‘우리 아이의 오늘을 남기고, 비슷한 시기의 엄마 아빠와 이야기를 나눠보세요.’
- 주요 행동: ‘우리 아이 이야기 남기기’ / ‘비슷한 시기 이야기 보기’
- 브랜드관·매거진·나들이 등 기존 기능은 보존하되 첫 화면에서 모두를 같은 비중으로 강조하지 않는다.
- 기존의 밝고 따뜻한 색, 둥글고 충분한 굵기의 글꼴, 편안한 클릭 요소를 유지한다. 전면 디자인 재개발은 하지 않는다.

**완료 기준**

- 두 행동이 실제 해당 흐름으로 연결되고, 인증 후 의도한 위치로 복귀한다.
- 기존 기능에 계속 접근할 수 있다.
- 320/360/390/430px 및 데스크톱에서 가로 넘침·겹침·버튼 잘림이 없다.
- 색 대비·초점 표시·키보드 이동·버튼 이름·터치 영역을 함께 확인한다.

### P1-2. 월령·주제에 맞는 글 발견

**수정 제안**

- 한 피드에서 월령과 주제로 탐색한다. 빈 게시판을 여러 개 신설하지 않는다.
- 첫 모집 대상 가설은 생후 6~12개월 보호자다. 서비스 전체를 이 연령으로 잠그지 않는다.
- 이유식·수면·기기·외출 등 실제 게시물을 찾을 수 있도록 기존 분류·필터를 우선 활용한다.
- 사용자의 기존 프로필 정보를 재사용하되 추가 아동 정보 입력을 불필요하게 강제하지 않는다.

**완료 기준**

- 조건 초기화·뒤로 가기·새로고침 시 일관된 동작을 한다.
- 조건에 맞는 글이 없으면 거짓 추천·가짜 활동량 대신 조건 완화나 전체 보기로 안내한다.
- 기존 검색·정렬·차단·검수·공개 정책을 우회하지 않는다.

### P1-3. 질문 이후의 후기 연결

**수정 제안**

- ‘그 뒤 어떻게 됐나요?’에 해당하는 후기를 원래 질문과 연결할 최소 방식을 찾는다.
- 기존 댓글·답글·글 수정·관련 글 기능으로 충분하면 새 테이블·새 게시판을 만들지 않는다.
- 후기 작성은 선택이다. 강제 알림·반복 독촉은 만들지 않는다.

**완료 기준**

- 질문과 연결된 후기를 이용자가 알아볼 수 있다.
- 타인의 글을 수정하거나 비공개 기록을 공개 후기와 자동 결합할 수 없다.
- 원글 삭제·차단·검수 변경·공개 범위 변경 시 연결 자료도 정책에 맞게 처리된다.
- 경험담을 전문가 진단이나 효과 보장처럼 표시하지 않는다.

## 5. P2 — 작은 실험으로 확장

### P2-1. 가족 한 줄 참여 — 가장 먼저 시험할 가족 기능

**목표 흐름**

`기록자: 기존 성장 순간 선택 → 허용된 가족에게 공유 → 수신자: 브라우저에서 권한 확인 → 해당 순간 열람 → 선택적으로 한 줄 반응`

**요구사항**

- 앱 설치를 선행 조건으로 두지 않는다. 필요한 인증·가족 확인은 유지한다.
- 이미 올린 사진을 다시 업로드하거나 기록을 다시 입력하지 않게 한다.
- 가족의 메시지를 기존 순간에 연결하되 공개 댓글·경품 투표와 구분한다.
- 기존 가족 공유와 서버 기록 기능을 먼저 확인한다. 별도 가족 시스템을 중복 구축하지 않는다.
- 초대 만료·철회·재공유·탈퇴·로그아웃·다른 계정 열람을 고려한다.

**완료 기준**

- 유효한 가족은 공유한 자료로 도달한다. 미가입자·기존 가입자 흐름을 구분해 검증한다.
- 권한 없는 사람과 철회·만료된 초대로는 자료에 접근할 수 없다.
- 아이 사진이 공유 미리보기나 외부 수집 이벤트로 새어 나오지 않는다.
- 메시지로 응원 점수·투표권·순위가 바뀌지 않는다.
- 보내는 사람의 중복 작업과 수신자의 단계 수를 기록해 기존 흐름과 비교한다.
- iPhone Safari 및 카카오톡 등 실제 공유 진입 경로는 검증한 범위와 사용자 직접 확인이 남은 범위를 구분한다.

첫 실험 후 관찰할 항목: 열람, 반응 완료, 두 번째 이용, 주 기록자 부담, 카카오톡 대비 실제 선호. 낮은 반응을 남편의 무관심으로 단정하지 않는다. 공유 계기·인증 부담·가치 전달을 함께 본다.

### P2-2. 커뮤니티 경험과 개인 성장 기록 연결

- 공개 글·후기의 선택적 개인 저장부터 검토한다.
- 질문·후기·사진을 연결하되 별도 입력을 최소화한다.
- 가족 전용·개인 기록을 자동 공개하지 않는다. 개인 저장이 공개 게시를 뜻하지 않게 한다.
- 하나의 자료를 재사용할 때 원본 삭제·권한 변경·연결 해제의 동작을 명시한다.
- 글과 기록의 동시 수정 충돌, 실패 재시도, 중복 저장, 다른 기기 동기화를 관련 변경 범위에서 확인한다.

### P2-3. 챌린지의 비경품 가치 확인

- 경품이 없어도 성장 순간을 남기는 동기를 관찰한다.
- 현재 응원·투표·점수·자격·경품 규칙은 임의 변경하지 않는다.
- 가족 반응을 공식 투표로 전환하지 않는다.
- 별도 비경품 활동 도입은 현재 챌린지 수정과 구분해 제품 범위를 정한 후 진행한다.
- 단순 참여자 수 대신 일반 기록·대화·이후 참여를 함께 본다.

### 이후 검토할 남편·가족 참여 유형

| 유형 | 최소 행동 | 개발 판단 |
|---|---|---|
| 초대받아 보는 사람 | 열람·한 줄 반응 | 첫 가족 실험 |
| 사진을 찍는 사람 | 본인이 찍은 자료 하나 전달 | 첫 실험 후 필요 확인 |
| 돌봄을 함께 하는 사람 | 본인이 한 돌봄 내용 하나 기록 | 기존 돌봄 기능 활용부터 |
| 의견을 내는 사람 | 질문 하나에 경험·선택 이유 남기기 | 커뮤니티 흐름 재사용 |
| 적극 기록자 | 직접 기록·챌린지 참여 | 기존 기능 유지 |

아빠 전용 메뉴·순위·미션·의무 기록을 한꺼번에 신설하지 않는다. 반응과 돌봄 분담은 별도로 해석한다.

## 6. P3 — 이용 근거 확보 후 사업화 지원

- 작은 브랜드와 주제형 협업을 우선 검토한다. 예: 이유식 대화가 실제 생긴 뒤 관련 제품 체험.
- 기존 브랜드관·협찬 표시·체험단 기능을 먼저 확인한다.
- 광고·협찬 표시, 솔직한 후기 조건, 체험 모집·종료 상태를 명확히 한다.
- 긍정적인 후기를 강제하거나 가상 후기를 실제 이용자 후기처럼 게시하지 않는다.
- 큰 경품, 대규모 입점, 신규 결제·정산 시스템은 이용 근거 확보 전 보류한다.
- 외부 업체 메시지 발송·광고 집행·비용 지출은 코드 수정 권한에 포함되지 않는다.

## 7. 한 달 일정과 개발 범위 연결

| 기간 | 제품·운영 목표 | AI 개발·검증 범위 | 산출물 |
|---|---|---|---|
| 1주차 | 대상·첫 경험 좁히기 | P0 확인, 필요한 P1 최소 변경 | 현재 상태·변경 목록·테스트 결과·측정 정의 |
| 2주차 | 5~8명 사용성 확인 | 가입·탐색·작성·답변·공유에서 발견한 오류 우선 수정 | 막힌 단계·원인·수정·재검증 기록 |
| 3주차 | 같은 시기 30~50가구 목표 제한 모집 시작 | 승인된 작은 흐름 제공, 유입·행동 집계 검증 | 유입 출처별 관찰 자료 |
| 4주차 | 실제 답변·재방문·비경품 행동 확인 | 필요한 오류 수정과 분석, 무관한 새 기능 추가 자제 | 집중할 흐름·보류할 기능·다음 실험 제안 |

5~8명은 사용성 확인용이고, 30~50가구는 제한 운영의 제안 규모다. 시장 수요나 통계적 성공을 보장하는 표본 수가 아니다. 모집·답변 운영·브랜드 협의는 운영 업무다. 가상 계정을 늘려 실제 참여 지표를 채우지 않는다.

모집은 사전 협의 QR·동의한 콘텐츠 운영자·예산 상한을 둔 소액 광고로 출처를 구분한다. 무단 카페 홍보는 전제하지 않는다. 초기에 운영자가 답변하면 운영자임을 표시한다.

## 8. 검증·배포 원칙

### 구현 전후 공통

- 현재 관련 구현과 테스트를 읽고, 실제 변경에 맞는 검증을 선택한다. 예전 테스트 통과 수를 최신 변경의 결과로 재사용하지 않는다.
- 접근 제어 변경은 허용 사용자, 타인, 비로그인, 철회·만료 상태를 함께 확인한다.
- HTTP 성공 코드만으로 데이터 변경 성공·차단을 판단하지 않고 테스트 DB에서 결과를 다시 읽는다.
- 사용자 자료 대신 가상 테스트 자료를 사용하고 자신이 만든 자료만 정리한다.
- DB 변경이 필요하면 기존 마지막 마이그레이션 번호를 확인한다. 예전 0013·0017 등 적용 완료 작업을 재실행하지 않는다.
- 저장소 규칙대로 DB 대시보드 작업과 코드 수정 세션을 분리한다. 필요한 DB 변경은 마이그레이션·리허설·역방향 계획과 함께 별도 전달한다.

### UI 변경 시

- 관련 자동 검증 후 staging 배포가 승인 범위에 있으면 테스트 사이트에서 확인한다.
- 빌드·캐시·서비스워커를 확인하고 실제 수정 버튼을 누른다.
- 홈·피드·상세 등 같은 버튼이 여러 화면에 있으면 각각 확인한다.
- 화면 상태와 테스트 DB 저장 결과가 일치하는지 본다.
- 320/360/390/430px와 데스크톱을 확인하고 iPhone 실제 기기 미검증은 명시한다.
- 이번 변경만 되돌릴 방법을 기록한다. 기존 사용자 변경까지 되돌리지 않는다.

운영 이관은 이 전달서의 범위가 아니다. 테스트 결과를 정리하고 종료한다. 운영 이관 지시가 별도로 오면 `docs/PROMOTION.md`와 해당 승인 범위를 따른다.

## 9. 다음 AI의 결과 보고 형식

1. **확인한 현재 상태** — 최신 브랜치·기준 커밋, 기존 변경, 이미 구현된 기능
2. **실제 수정한 내용** — 우선순위·파일·변경 이유

4. **미완료** — 이유·의존 조건·사용자가 직접 확인할 단계

6. **남은 제품 판단** — 결과를 바탕으로 다음에 집중·보류할 항목
7. **환경 확인** — 운영 앱·운영 DB·실제 회원 데이터 미접촉 여부

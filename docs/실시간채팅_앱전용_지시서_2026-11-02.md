## 3. 만들 것 (가장 작은 범위)

### A. DB — 새 마이그레이션 `supabase/migrations/0057_live_chat.sql`

- 표 `chat_messages`
  - `id uuid` — **클라이언트가 만든다** (`INSERT ... RETURNING` 지뢰 피하기)
  - `room text not null default 'all'` — 지금은 방 하나. 나중에 출산 예정월·지역별 방을 위해 칸만 둔다
  - `user_id uuid`, `nickname text` — 서버 트리거가 `auth.uid()` 와 프로필 닉네임으로 채운다 (클라이언트 값 무시)
  - `body text` — 1~200자
  - `hidden boolean default false`, `created_at timestamptz default now()`
- 보내기 전 검사(트리거)
  - `mod_hold_text(body)` 에 걸리면 **거절**하고 이유를 돌려준다 (채팅은 검수 대기가 없다)
  - 같은 사람이 **3초 안에** 또 보내거나, **직전과 같은 내용**이면 거절 (도배 막기)
- 읽기·쓰기 규칙(RLS)
  - 읽기: 로그인한 사람만. `hidden` 글 제외(관리자는 다 봄). `is_blocked(user_id)` 인 사람 글 제외
  - 쓰기: 로그인한 본인만
  - 고치기·지우기: 관리자만 (일반 회원은 자기 글도 못 고침)
- 실시간 켜기: `alter publication supabase_realtime add table public.chat_messages;`
  (`postgres_changes` 를 쓰면 읽기 규칙이 실시간에도 그대로 적용된다)
- 신고: `reports.target_type` 에 `'chat'` 추가, `mod_report_autohide()` 가 `'chat'` 이면 `hidden = true`
- 보관: `pg_cron` 으로 **30일 지난 채팅 매일 삭제** (기본값, 8번 참고)
- 새 함수는 `revoke execute ... from public, anon` — **`public` 을 꼭 같이** (4번 지뢰)

### B. 화면 — `index.html`

- **입구**: 앱이면 커뮤니티 화면 위쪽에 "실시간 채팅" 입구. 웹이면 같은 자리에 "앱에서 채팅하기" 안내(플레이스토어 링크)
- **처음 들어올 때**: 이용 규칙 한 번 동의 (욕설·광고·연락처·개인정보 금지, 어기면 숨김·제재). 앱 심사에 필요
- **채팅 화면**
  - 최근 50개 불러오고, 새 글은 실시간으로 아래에 붙인다
  - 닉네임·시각 표시, 내 글은 오른쪽
  - 위로 올려 보는 중이면 자동으로 내려가지 않고 "새 메시지" 버튼
  - 위쪽에 **지금 들어와 있는 사람 수** (Presence)
  - 입력창 200자, 보내기 실패하면 **이유를 화면에 보여준다** (실패를 삼키지 않는다 — 4번 지뢰)
  - 남의 글을 누르면 **신고**(기존 `REPORT_REASONS`) / **차단**
- **나갈 때**: 채널 연결을 끊는다 (동시 접속 수가 곧 비용)
- 디자인은 `docs/디자인_리뉴얼_지시서_2026-11-02.md` 를 따른다. 이모지 아이콘 금지

## 4. 하지 않는 것

- 1:1 대화, 사진·영상·링크 미리보기, 여러 방 화면, 웹 채팅, 푸시 알림 연결
- **운영 반영** — 테스트 환경에서만. 운영은 `docs/PROMOTION.md` 절차 + 사장님 승인

### 이 작업에 걸리는 지뢰 (`CLAUDE.md` 4번)

- RLS 안에서 다른 표를 직접 읽지 말고 `security definer` 함수(`is_blocked()` 처럼)로 감싼다
- 함수 권한 회수는 `from public, anon` 으로
- PATCH/DELETE 가 막혀도 204 가 온다 → 테스트는 **값을 다시 읽어서** 확인
- 파괴적 SQL 은 `begin; ... rollback;` 으로 먼저 리허설

## 7. 검증

1. **DB 시험** (`tests/live-chat.spec.mjs`, 기존 `tests/auto-moderation.spec.mjs` 방식)
   - 비로그인 읽기·쓰기 막힘
   - 201자, 금지어, 3초 안 연속, 같은 내용 반복 → 거절되고 이유가 돌아옴
   - 남의 글 고치기·지우기 막힘 (값을 다시 읽어 확인)
   - 차단한 사람 글이 안 보임, 서로 다른 3명 신고 → 숨김
2. **실시간**: 테스트 계정 `momA`, `momB` 로 두 창을 열고, A가 보내면 B 화면에 1초 안에 뜨는지
3. **앱/웹 구분**: 일반 브라우저에서는 입구 대신 안내만 보이는지. `window.Capacitor` 를 앱처럼 흉내 내면 입구가 보이는지
4. **배포본에서 직접 눌러보기** (`CLAUDE.md` 8번): `staging` push 후 테스트 사이트에서 보내기·신고·차단을 실제로 눌러 화면 값과 DB 값을 둘 다 확인
5. 실제 앱(안드로이드)에서의 확인은 운영 이관 뒤 사장님 폰으로 한다 — 이관용 묶음만 준비

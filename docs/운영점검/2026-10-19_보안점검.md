## 2. 괜찮은 것 (경고는 뜨지만 의도대로)

- `SECURITY DEFINER` 함수를 로그인 사용자가 부를 수 있다는 경고 다수 — 앱이 부르는 함수들이다.
  운영자용(`admin_applications`·`reveal_application_pii`·`pii_purge_stats`·`purge_expired_pii`)은
  전부 안에서 `is_admin()` 을 확인한다. 본인용(`delete_my_account`·`edit_my_*`·`my_media_paths`)은 `auth.uid()` 로만 동작.
- `_purge_expired_pii_job()`(0018)·카운터 동기화 트리거 함수는 아무 역할도 부를 수 없다.
- `admin_emails`·옛 `families` 표: RLS 켜짐 + 정책 없음 = 아무도 못 읽음. 운영 옛 `families` 는 0행이고,
  0016 이 0행이면 지우고 새로 만든다 (가족 공유 이관 때 막히지 않음).
- 0005(반응 조작 방지)·0012(가입 동의)·P0-05 단계 C(본문 표 개인정보 컬럼 삭제)는 운영에 들어가 있다.

## 3. 사장님 판단이 필요한 것

- **유출 비밀번호 차단(Leaked password protection) 꺼짐 — 운영·테스트 둘 다.** 가입할 때 이미 유출된 비밀번호를 거절하는 기능.
  Supabase 유료(Pro) 요금제에서만 켤 수 있다. 요금제를 올릴 때 같이 켜는 것을 권함.

## 4. 낮은 위험 — 기록만

- `owns_application(app_id, uid)`·`media_can_read(obj_name, uid)` 는 RLS 안에서 쓰려고 만든 함수인데
  API 로도 부를 수 있고 `uid` 를 아무 값이나 넣을 수 있다. 신청 id·파일 경로를 이미 알아야 "그 사람이 주인인가"만 알 수 있어
  실질 위험은 낮다. 고치려면 API 노출 스키마 밖으로 옮겨야 해서 RLS 정책을 같이 바꿔야 한다 — 다음 보안 작업 때.
- 운영에만 있는 인덱스 5개(`idx_*_owner`, `idx_notices_created`)는 성능용이라 그대로 둔다. 테스트에 없는 것은 무해.
